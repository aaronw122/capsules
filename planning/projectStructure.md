# Project Structure

## How React Native Projects Are Structured

A React Native app is **one project with two runtimes**. Your TypeScript code and your native Swift code live side-by-side in the same repo, but they run in different environments:

```
capsules/                         <- One repo, one project
│
├── frontend/                     <- React Native app
│   ├── app/                      <- YOUR TypeScript code (runs in JS engine)
│   │   ├── (tabs)/
│   │   │   ├── index.tsx             # onboarding
│   │   │   ├── login.tsx             # put in name
│   │   │   ├── ar.tsx                # AR screen (wraps native view + lobby overlay + HUD + game over)
│   │   │   └── leaderboard.tsx       # Real-time leaderboard
│   │   ├── components/
│   │   │   ├── CapsuleDetail.tsx     # Modal on capsule tap
│   │   │   └── HUD.tsx               # Timer + progress overlay
│   │   ├── native/
│   │   │   ├── **ARWorldMapModule.ts   JS typed wrapper for native module (calls swift methods and listens for swift events)**
│   │   │   └── **ARWorldMapView.tsx    JS wrapper for native view (renders swift AR camera view as react component)**
│   │   └── game/
│   │       ├── state.ts              # Player state, derived state
│   │       └── **api.ts              # HTTP + WebSocket client for backend (hooks)**
│   │
│   ├── ios/                      <- Native iOS project (runs in iOS runtime)
│   │   ├── frontend/             <- Auto-generated Xcode boilerplate (DON'T EDIT)
│   │   │   ├── AppDelegate.mm       # RN startup glue (generated)
│   │   │   ├── Info.plist            # App permissions, config (generated, you may edit)
│   │   │   └── ...                   # ~10 files, all generated by Expo prebuild
│   │   ├── CapsuleAR/            <- YOUR Swift code (you create this folder)
│   │   │   ├── ARWorldMapView.swift            # ARSCNView wrapper, renders capsules, handles taps
│   │   │   ├── ARWorldMapModule.swift          # Imperative methods + event emitter
│   │   │   ├── ARWorldMapViewManager.swift     # Exposes view to RN
│   │   │   ├── ARWorldMapViewManager.m         # ObjC bridge declaration
│   │   │   ├── ARWorldMapModule.m              # ObjC bridge declaration
│   │   │   └── CapsuleAR-Bridging-Header.h    # Swift <-> ObjC interop
│   │   └── frontend.xcodeproj    <- Xcode project file (generated)
│   │
│   ├── .eslintrc.js              <- ESLint config (TypeScript/React rules)
│   ├── tsconfig.json
│   └── package.json
│
├── backend/                      <- Express + WebSocket server
│   ├── data/
│   │   └── capsules.json            # Merged capsule data (positions + content, single source of truth)
│   ├── src/
│   │   ├── index.ts              # Express app entry + WebSocket setup + HTTP routes
│   │   │                         #   GET /capsules — serves merged capsule data
│   │   │                         #   POST /addPlayer — registers player, returns player ID
│   │   │                         #   POST /admin/start — host triggers game start (curl from terminal)
│   │   ├── ws/
│   │   │   └── handler.ts        # WebSocket: all in-game communication
│   │   │                         #   Receives: openCapsule, submitPhrase
│   │   │                         #   Broadcasts: gameStart (with endsAt), gameOver, leaderboardUpdate
│   │   └── state/
│   │       └── game.ts           # Server-side game state (timer, leaderboard, players)
│   ├── .eslintrc.js              <- ESLint config (Node/Express rules)
│   ├── tsconfig.json
│   └── package.json
│
├── capture-tool/                 <- Separate Xcode project (Erik's dev tool)
│   ├── CaptureApp.xcodeproj
│   └── CaptureApp/
│       └── CaptureApp.swift      # ~100 lines, standalone
│
└── planning/                     <- Docs
    ├── planning.md
    ├── reactBridge.md
    └── projectStructure.md
```

## There Is No Duplication

| Folder | Who creates it | What it does | Do you edit it? |
|--------|---------------|--------------|-----------------|
| `frontend/app/` | You | All TypeScript — screens, game logic, components | Yes, most frontend dev happens here |
| `frontend/ios/frontend/` | `npx expo prebuild` | Xcode boilerplate — wires RN's JS engine to iOS | No (regenerated on prebuild) |
| `frontend/ios/CapsuleAR/` | You | Your custom Swift AR module | Yes, Erik writes this |
| `frontend/ios/frontend.xcodeproj` | `npx expo prebuild` | Xcode project config | Rarely (to add CapsuleAR files to the build) |
| `backend/data/` | Erik (capture tool) + content author | capsules.json — merged positions + content, single source of truth | Yes, when venue is captured or content changes |
| `backend/` | Beckham | Express server — HTTP routes, WebSocket, game state | Yes |
| `capture-tool/` | Erik | Standalone venue capture app | Yes, separate from main app |

## Linting — Separate Per Layer

Each layer has its own linting toolchain. They don't share config because they're different languages and runtimes.

| Layer | Tool | Config location | What it checks |
|-------|------|----------------|----------------|
| `frontend/app/` (TypeScript) | ESLint + Expo config | `frontend/.eslintrc.js` | React components, TS types, import rules |
| `backend/` (TypeScript) | ESLint + Node config | `backend/.eslintrc.js` | Express routes, Node APIs, no browser globals |
| `frontend/ios/CapsuleAR/` (Swift) | SwiftLint (optional) or Xcode warnings | `frontend/ios/.swiftlint.yml` | Swift style, ARKit patterns |
| `capture-tool/` (Swift) | Xcode warnings | N/A | Not worth linting — throwaway dev tool |

Frontend and backend are both TypeScript but need **different ESLint configs** because:
- Frontend allows React JSX, browser APIs, `import` syntax
- Backend allows Node APIs (`process`, `require`), no JSX, Express patterns

Each has its own `package.json` and runs `bun run lint` independently.

## Why `ios/capsules/` Exists and What It Is

When you run `npx expo prebuild`, Expo generates a full native Xcode project. This includes:
- `AppDelegate.mm` — boots up React Native's JS engine
- `Info.plist` — declares camera permissions, app name, etc.
- Build settings, linking config, CocoaPods setup

**This is scaffolding, not your app.** Think of it like `node_modules` — it's generated infrastructure that makes your code run. Your actual app logic lives in `app/` (TypeScript) and `ios/CapsuleAR/` (Swift).

---

## Why Swift Code Lives Inside `ios/` and Not Alongside `app/`

Swift must be compiled by Xcode as part of the iOS build. Xcode only sees files inside the `ios/` directory. If you put Swift files next to `app/`, Xcode wouldn't know they exist. So:

- `app/` = everything the **JS engine** runs (TypeScript, React components)
- `ios/CapsuleAR/` = everything **Xcode compiles** into the native binary (Swift, ObjC bridge)

They talk to each other through the bridge at runtime, but they're compiled by different tools.

## Two Separate Apps

There are **two Xcode projects**, not one. This decouples venue capture from the main app and removes the TestFlight dependency for world map generation.

### 1. Capture Tool (`capture-tool/`)

A standalone Swift app, ~100 lines. Erik runs it on his phone directly from Xcode (plugged in via USB, no TestFlight needed). Used to scan the venue and place capsule positions.

- Runs ARKit session, tap to place capsules, save world map
- Exports `positions.json` + `worldmap.arworldmap`
- Never goes to TestFlight — dev tool only
- If the venue changes or lighting shifts, Erik re-runs in 5 minutes

### 2. Main App (`ios/` + `app/`)

The React Native + Swift app that players install via TestFlight. It **consumes** the files from the capture tool. It never needs to generate a world map or place capsule positions itself.

| | Capture Tool (Erik) | Main App (Players) |
|---|---|---|
| ARKit session | Yes | Yes |
| Raycast / place new capsules | Yes | No |
| Save world map | Yes | No |
| Load world map | No | Yes |
| Relocalize | No | Yes |
| Render capsules at positions | Yes (preview spheres) | Yes (final 3D models) |
| RN bridge | No | Yes |
| TestFlight | No | Yes |

## File Descriptions

### `frontend/app/native/` — Bridge Consumers (TypeScript)

**`ARWorldMapModule.ts`** — JS typed wrapper around the native module
- Exposes: `startSession()`, `placeCapsules()`, `pauseSession()`
- Subscribes to native events via `NativeEventEmitter`

**`ARWorldMapView.tsx`** — JS wrapper for the native view
- `requireNativeComponent("ARWorldMapView")`
- Renders the Swift AR view as a React component: `<ARWorldMapView style={{flex: 1}} />`

### `frontend/ios/CapsuleAR/` — Native AR Module (Swift)

**`ARWorldMapView.swift`** — The actual AR view
- Subclasses `ARSCNView`
- Runs the ARKit camera session
- Renders 3D capsule nodes in world space
- Handles tap gesture -> `SCNHitTest` -> finds `node.name` (capsule ID)
- `placeCapsules([{id, position}])` — creates `SCNNode`s, sets `node.name = id`
- `loadWorldMap(filename)` — deserializes and relocalizes

**`ARWorldMapModule.swift`** — Imperative methods + events
- Methods RN can call: `startSession()`, `placeCapsules()`, `pauseSession()`
- Emits events back to RN: `onCapsuleTapped`, `onRelocalized`, `onTrackingStateChanged`

### `frontend/ios/CapsuleAR/` — Bridge Glue (ObjC)

**`ARWorldMapViewManager.swift`** — Exposes ARWorldMapView as a RN `<View>`

**`ARWorldMapViewManager.m`** — One-liner: `RCT_EXTERN_MODULE(ARWorldMapView, RCTViewManager)`

**`ARWorldMapModule.m`** — `RCT_EXTERN_MODULE` / `RCT_EXTERN_METHOD` declarations

**`CapsuleAR-Bridging-Header.h`** — `#import <React/RCTBridgeModule.h>` etc.

The `.m` files are one-liners that tell React Native "these Swift classes exist." The bridging header lets Swift import React Native's ObjC types.

### `backend/data/` — Capsule Data (Single Source of Truth)

**`capsules.json`** — Merged positions + content, served by the server
- `[{ "id": "asd124b", "position": [2.1, 0.5, -3.4], "label": "Beckham", "letter": "F", "content": {...} }, ...]`
- Erik produces positions from capture tool, content is authored separately, then merged into this one file
- Client fetches once on app load via `GET /capsules`, then splits:
  - `[{id, position}]` → sent to Swift via bridge for AR rendering
  - `[{id, label, letter, content}]` → kept in React state for game logic
- Update this file without rebuilding the app — just restart the server

### `frontend/app/game/` — Game Logic

**`state.ts`** — Player state and derived state (discovered capsules, phrase progress, win condition)

**`api.ts`** — HTTP + WebSocket client for communicating with the backend
- HTTP: `GET /capsules` (on app load), `POST /addPlayer` (on join)
- WebSocket: all in-game communication (openCapsule, leaderboard updates, game state changes)

### `backend/src/` — Express + WebSocket Server

**`index.ts`** — App entry point + HTTP routes
- Express app setup + WebSocket server initialization
- `GET /capsules` — reads `data/capsules.json`, serves to client
- `POST /addPlayer` — registers player name, returns player ID
- `POST /admin/start` — host hits this from terminal (`curl`) to start the game

**`ws/handler.ts`** — WebSocket: all in-game communication
- Receives from clients: `openCapsule`, `submitPhrase`
- Broadcasts to all clients: `gameStart` (with `endsAt` timestamp), `gameOver`, `leaderboardUpdate`

**`state/game.ts`** — Server-side game state
- Timer (startTime + duration, server triggers gameOver when expired)
- Leaderboard (all players sorted by discoveredCount, then completedAt)
- Game status (lobby, playing, gameOver) — server is the single authority for state transitions
